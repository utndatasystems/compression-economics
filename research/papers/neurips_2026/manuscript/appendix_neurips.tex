\subsection{Metric Definitions}
For a token sequence $x$ of length $N$, let $B(x)=\bytes{\operatorname{decode}(x)}$ be its decoded UTF-8 size in bytes, $L_\theta(x)$ its model negative log-likelihood in bits, and $S_{\mathrm{AC}}(x)$ its arithmetic-coded payload in bits. The metrics reported in Table \ref{tab:decisive} (prediction cost and tokenizer fertility per token, predictive coding cost per source byte) are re-stated here in more detail:
\begin{align}
  \text{Prediction cost} &= \frac{L_\theta(x)}{N}
    && [\mathrm{bits/token}],\\
  \text{Tokenizer fertility} &= \frac{B(x)}{N}
    && [\mathrm{bytes/token}],\\
  \text{Ideal predictive rate} &= \frac{L_\theta(x)}{B(x)}
    && [\mathrm{bits/byte}],\\
  \text{Realized AC rate} &= \frac{S_{\mathrm{AC}}(x)}{B(x)}
    && [\mathrm{bits/byte}].
\end{align}

The ideal rate factorizes as
$L_\theta(x)/B(x)=[L_\theta(x)/N]/[B(x)/N]$: high prediction cost can therefore
be offset when each token represents many source bytes. To compare encoded
sizes directly with raw UTF-8, we report
\begin{align}
  R_{\mathrm{AC}}(x)
    &=100\,\frac{S_{\mathrm{AC}}(x)}{8B(x)},\\
  R_{\mathrm{real}}(x)
    &=100\,\frac{\left|\operatorname{SerializeCodec}(x)\right|}{B(x)}.
\end{align}
Here $R_{\mathrm{AC}}$ covers only the arithmetic payload, whereas
$R_{\mathrm{real}}$ covers the complete serialized stream in bytes, including
its dictionary, metadata, and framing. Both are percentages of the raw source
size: values below $100\%$ denote compression and values above $100\%$ denote
expansion.

\subsection{Adversarial Input Construction}
\label{app:attack-algorithms}

The adversarial input is built one token at a time. At every step, (1) the model produces scores for the next possible continuation token in the vocabulary, (2) ranks the candidate tokens according to the attack objective (\MinProb{}, \MaxSurprisal{}), and (3) tries candidates in that order until it finds one
that remains unchanged after decoding and re-tokenization. The accepted token is
then appended and the process repeats.

\sparagraph{Canonical Inputs.}
\label{app:canonicality}
Not every sequence of valid token IDs can be produced from tokenizing its own decoded bytes. For example, suppose the vocabulary contains tokens for
\texttt{a}, \texttt{b}, and \texttt{ab}. The token sequence $[\texttt{a},\texttt{b}]$ decodes to \texttt{ab}, but the tokenizer may encode \texttt{ab} as the single token $[\texttt{ab}]$. Hence, decoding and re-tokenizing changes the token sequence. Since our attacks select token IDs directly from the model distribution, allowing such sequences would optimize over token histories that cannot occur for the corresponding source input. It is therefore imperative to require every generated partial sequence to be canonical, i.e., $T(\operatorname{decode}(x_{1:t}))=x_{1:t}$. This ensures that final decoding recovers exactly the same token IDs and bytes.

\sparagraph{Candidate Pool.} We begin with every token ID shared by the tokenizer and model, then remove all IDs listed in \texttt{tokenizer.all\_special\_ids}. This excludes EOS, padding, chat markers, and other tokenizer-declared control tokens. The resulting pool contains 151,643 IDs for Qwen2.5-0.5B. The notation $G(h)$ in the main paper means the members of this pool that have a finite model score and pass the exact round-trip check in Algorithm~3 after prefix $h$. Admissibility depends only on the current prefix and proposed next token; there is no lookahead ("\textit{one-step-greedy")}.

\sparagraph{Evaluation Costs per Step.} Neither attack round-trip tests the full candidate set according to Algorithm~3: candidates are ranked first and canonicality is checked only until one is accepted. MaxSurprisal/Byte additionally computes the context-dependent decoded-byte increment for every candidate before ranking and discards non-positive increments, whereas \MinProb{} has no byte-length constraint. Computing increments from the complete decoded prefix captures tokenizer-boundary effects, while the round-trip check rejects candidates whose decoding changes the proposed token IDs.

\paragraph{Speeding up the Round Trip Check with an Exact Fallback.} Algorithm~3 defines the acceptance criterion used throughout. To avoid re-tokenizing the entire prefix for every candidate, the implementation uses a faster suffix check whenever it can guarantee that the earlier part of the prefix is unaffected. For each accepted prefix, it caches the decoded text, byte offsets, token boundaries, and pre-tokenizer pieces. It then re-tokenizes only a short suffix when several safety conditions hold, including that the suffix starts at a token boundary, is at most 512 bytes long, begins with ASCII, and its earlier tokenization remains unchanged after adding the candidate. If these conditions cannot be verified, the full-prefix check runs.

\begin{center}
\fbox{\begin{minipage}{0.94\linewidth}
\textbf{Algorithm 1: \MinProb{} ($\vtok$)}
\smallskip

\textbf{Input:} a non-empty seed prefix $h$ and target length $N$.
\begin{enumerate}
  \item Ask the model for the next-token logits.
  \item Remove candidates with non-finite logits. Sort the rest from lowest
        logit to highest logit; for equal logits, place the lower token ID first.
  \item In that order, apply Algorithm~3. Append the first candidate that passes.
  \item Repeat until the complete sequence, including the seed, has $N$ tokens.
\end{enumerate}
\textbf{Output:} the completed token sequence $h$.
\end{minipage}}
\end{center}

\begin{center}
\fbox{\begin{minipage}{0.94\linewidth}
\textbf{Algorithm 2: \MaxSurprisal{} ($\vbyte$)}
\smallskip

\textbf{Input:} a non-empty seed prefix $h$ and target length $N$.
\begin{enumerate}
  \item Ask the model for the next-token logits and compute float32 log
        probabilities over the full tokenizer vocabulary.
  \item For every finite candidate $v$, decode the complete prefixes $h$ and
        $h\Vert v$ and measure
        $d_v=|\Dec(h\Vert v)|_{\mathrm{UTF8}}-|\Dec(h)|_{\mathrm{UTF8}}$.
        Remove candidates for which $d_v\leq0$.
  \item Rank the remaining candidates by decreasing
        $-\log_2 p(v\mid h)/d_v$; for equal scores, place the lower token ID first.
  \item In that order, apply Algorithm~3. Append the first candidate that passes.
  \item Repeat until the complete sequence, including the seed, has $N$ tokens.
\end{enumerate}
\textbf{Output:} the completed token sequence $h$.
\end{minipage}}
\end{center}

\begin{center}
\fbox{\begin{minipage}{0.94\linewidth}
\textbf{Algorithm 3: Exact round-trip check}
\smallskip

\textbf{Input:} the accepted prefix $h$ and proposed token $v$.
\begin{enumerate}
  \item Decode $h\Vert v$ with special-token skipping and tokenizer cleanup
        disabled.
  \item Retokenize the decoded text with
        \texttt{add\_special\_tokens=False}.
  \item Accept $v$ exactly when the resulting IDs equal $h\Vert v$; otherwise
        reject it and test the next ranked candidate.
\end{enumerate}
\textbf{Output:} accept or reject.
\end{minipage}}
\end{center}

\subsection{Experimental Setting and Evaluation Protocol}
\label{app:experimental-details}

\sparagraph{Model and Coder.} We chose Qwen2.5-0.5B because its small size makes full-vocabulary adversarial scoring tractable while retaining a large vocabulary, and allows the experiments to run locally on a CPU without requiring GPU access. We use 151,643 non-special candidates, a 1,000-token context with 100 tokens retained between coding blocks, and KV caching. Arithmetic coding uses a 32-bit state and frequency total 262,144. The version-1 Qwen+AC stream records the seed, model and coder configuration, token and raw-byte counts, arithmetic payload, any required token dictionary, and framing. Model weights and the shared tokenizer table are shared decoder state and excluded from both Qwen representations.

\sparagraph{Inputs and Aggregation.}
The primary evaluation uses 10,000-token sequences for natural text, random canonical input, \MinProb{} ($\vtok$), and the one-byte UTF-8 ablation. \MaxSurprisal{} ($\vbyte$) is reported at the largest feasible budget of 1,024 tokens and is the final evaluation for that attack. The reported values for the other adversarial conditions are means over three independent canonical seed runs; the \MaxSurprisal{} ($\vbyte$) result is a single run.


\sparagraph{Round-Trip Validation and Baselines.}
All generated prefixes satisfy
\[\Tok(\Dec(x_{1:t}))=x_{1:t}, \qquad t=1,\ldots,N,\]
and every complete stream is independently decoded back to identical token IDs or UTF-8 bytes, as applicable. FSST is evaluated using the authors' reference implementation~\citep{boncz2020fsst}; Brotli uses quality~11; and the Qwen token IDs baseline stores each ID in a fixed-width 18-bit representation with a stream header.

\subsection{Arithmetic-Coder Quantization Sensitivity}
\label{app:quantization-sensitivity}
A practical real-world observation is that the coder cannot consume arbitrarily small probabilities. For a coding alphabet of size $K$ with frequency total $T$, it constructs
\begin{equation}
    f_i = 1 + \lfloor (T-K)p_i\rfloor + r_i, \qquad q_i=f_i/T,
\end{equation} \label{eq:quantization_floor}
where $r_i\in\{0,1\}$ distributes the counts left after flooring in
descending model-probability order. The leading one makes every token decodable, but also imposes $T\ge K$ and a probability floor $p_{\min}=1/T$.

Thus $2^{14}$ would be infeasible for the full $K=151{,}665$ coder alphabet. The coder alphabet includes the 22 tokenizer IDs excluded from attack selection, hence 151{,}665 rather than 151{,}643.

Our reported setting, $T=2^{18}$, leaves $T-K=110{,}479$ counts to represent differences after reserving one count per token. We define a selected token as \emph{clipped} when it receives only that mandatory count.

To test the effect quantization has in practice, Table~\ref{tab:quantization-sensitivity} replays the fixed adversarial token sequences at frequency totals $T\in\{2^{18},2^{22},2^{26},2^{30}\}$; $2^{30}$ is the largest value that the 32-bit coder implementation can handle. The model, token sequences, decoded bytes, context policy, and arithmetic-coder state size are all held fixed.

The lossless stream can emit only the $K$ tokenizer IDs, so the coder first restricts to that support and re-normalizes. For \MinProb{} $\vtok$ this support restriction reduces the ideal rate from 4.10 to 3.79 bits/byte; integer-frequency
quantization then reduces it to 2.534 bits/byte at $T=2^{18}$. This decomposition
prevents the whole model-ideal--AC gap from being attributed to integer rounding.

For \MinProb{} at $T=2^{18}$, 99.0\% of selected tokens are clipped. Raising $T$ monotonically toward the support-restricted ideal shows the following: at the maximum $T=2^{30}$, clipping falls to 13.8\% and realized AC rises to 3.735 bits/byte (46.7\% of raw UTF-8), compared with 2.534 bits/byte (31.7\%) at
$2^{18}$. Quantization therefore affects the numerical \MinProb{} rate,
but does not overturn the tokenization result: even the maximum-precision
payload remains less than half of raw size because \MinProb{} has high fertility.
For \MaxSurprisal{}, realized AC changes from 9.790 to 10.481 bits/byte
(122.4\% to 131.0\% of raw) and remains decisively expansive.

Across every row, realized AC differs from quantized ideal by at most 0.002 bits/byte. The reported surprisal error is $\Delta s=-\log_2q_i+\log_2p_i$ after
restricting $p_i$ to coder support; Table~\ref{tab:quantization-sensitivity}
reports its per-token mean and maximum absolute value.

\subsection{Reproducibility and Code Availability}
\label{app:reproducibility}
The code package to reproduce the experiments contains the implementation, a minimal CPU-only environment, and an experiment entry point.

\sparagraph{Environment and Hardware.} The reported environment uses Python~3.12.3; the complete dependency graph and package hashes are recorded in \texttt{uv.lock}. Key installed versions are PyTorch~2.10.0, Transformers~5.3.0, tokenizers~0.22.2, NumPy~2.4.3, and Brotli~1.2.0. Experiments ran CPU-only under Ubuntu~24.04.1 on one Intel Xeon Gold 5318Y processor (24 physical cores, 48 hardware threads) with 128~GiB RAM.

\sparagraph{Model and Data Availability.}  We use \texttt{Qwen/Qwen2.5-0.5B} and the authors' reference implementation of FSST, with all artifacts pinned to exact revisions.\footnote{Qwen revision: \texttt{060db6499f32faf8b98477b0a26969ef7d8b9987}; \\ FSST commit: \texttt{e638d4cf8c26129d73c242a4127b42b975de5b63};\\
text8 SHA-256: \texttt{6e890197040d37d85beb962ae1f041ff1d9a9ca8d20c7d99c85027eebf51dca7}.}

\sparagraph{Cross-Hardware Reproduction.} We independently reproduced the reported results on two different hardware platforms: a CPU-only server and a high-performance GPU cluster using NVIDIA H100 accelerators under Slurm. For the completed comparable conditions, most experiments reproduced exactly at the precision reported in Table~\ref{tab:decisive}: natural text (text8), the random-canonical control, and the one-byte UTF-8 ablation. In the full-vocabulary \MinProb{} experiment, the largest relative discrepancy across prediction cost, tokenizer fertility, ideal predictive rate, and realized AC rate was $3.0\%$; the central byte-normalized ideal rate differed by only $0.1\%$. These small differences are consistent with hardware-dependent floating-point execution.
